# AI-assisted Sales Order intake (design, approved 2026-09-08)

Owner-approved proposal for creating a sales order from a photographed or
PDF'd **customer PO** dropped into a New Sales Order modal. Mirrors the
expected-receipt intake feature (docs/designs/expected-receipt-intake.md,
FACTORY rows 117/118) and reuses its pipeline wholesale. Owner rulings from
the approval review are folded in and marked **[A]**.

## Goal & flow

User drops a PNG/JPG/PDF (or ⌘V-pastes a screenshot) into the New Sales Order
modal → `POST /sales/orders/extract` stores the file (shared upload path,
`purchase_documents` row with `document_kind='sales'`) →
`POST /purchase-documents/{id}/extract` runs vision extraction with the
sales schema → `POST /sales/orders/match` deterministically matches customer +
lines → review screen → on approve, ONE sales order with its lines via the
existing creation logic, all in one transaction.

## Hard rules (in addition to everything in the ER design doc)

* **Reuse, don't duplicate**: `purchase_documents` is generalized with a
  `document_kind` column ('purchase' | 'sales') — no second table.
  `extraction.py` gets a `kind` parameter selecting schema/prompt. Upload,
  storage, dedupe, rate limits, and the review-card UI are shared code.
* **[A]** The `_upload_intake_document` refactor must leave the ER flow
  byte-identical: `tests/test_expected_receipt_extract.py` passes unchanged
  and is not modified.
* New table `customer_product_aliases`
  (customer_id, customer_item_code, customer_description, product_id,
  case_size_lb), learned on approval, latest wins.
* Fuzzy product suggestions are restricted to products with prior
  `sales_order_lines` for that customer; private-label products never appear
  as suggestions for any other customer, at any tier. Chain:
  alias → exact → restricted fuzzy → human.
* Customer PO number is required; dedupe on (customer_id, normalized PO
  number), warn + `force` — never a hard block.
* Quantities: cases by default; convert via case_size_lb only for
  alias/exact/chosen products; lb accepted when the PO says lb.
* The model never writes to the DB; extraction/matching/approval stay
  separate steps; approve rides the standard `get_transaction` path (readonly
  tripwire + write-response envelope apply).
* `openapi-gpt-v3.yaml` (Sales & Admin GPT) untouched — dashboard-only.

## Key facts from inspection (2026-09-08)

* There is **no** New Sales Order modal today — the dashboard SO tab has only
  a detail/edit modal; creation is GPT-only via `POST /sales/orders` (master
  key, not on `DASHBOARD_KEY_ALLOWLIST`). The modal is built new.
* `sales_orders` has no customer-PO column (PO numbers live in notes free
  text); migration 050 adds `customer_po` + dedupe index +
  `source_document_id`.
* `_tiered_product_search` has no label/customer filter — every restriction
  below is new logic. `products.customer_id` is a legacy **uuid** (not an FK
  to `customers.id` integer) and `customer_name` is free text: the only
  reliable private-label ownership signal is prior `sales_order_lines`.
* `create_sales_order` is inline in its endpoint; `order_number` comes from
  the `trg_order_number` DB trigger; status is hardcoded `'confirmed'`.
* `resolve_customer_id` tiers (exact → `customer_aliases` → fuzzy) and
  `GET /customers/search` already exist; the match step reuses the lookup
  tiers WITHOUT auto-create.
* `sales_order_lines.unit_price` is surfaced as `case_price` with
  `price_basis` derived per_case/per_lb/per_unit from `case_size_lb`.

## Migration 050 (`migrations/050_sales_doc_intake.sql`)

```sql
BEGIN;

-- Generalize purchase_documents: one intake pipeline, two document kinds.
ALTER TABLE public.purchase_documents
    ADD COLUMN IF NOT EXISTS document_kind text NOT NULL DEFAULT 'purchase'
        CHECK (document_kind IN ('purchase', 'sales'));
CREATE INDEX IF NOT EXISTS idx_purchase_documents_kind
    ON public.purchase_documents (document_kind);

-- Customer's wording → our product, learned on approval (latest wins).
-- Looked up by item code first, then description. alias_key gives one
-- unambiguous ON CONFLICT target per (customer, code-or-description).
CREATE TABLE IF NOT EXISTS public.customer_product_aliases (
    id                   integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_id          integer NOT NULL REFERENCES public.customers(id),
    customer_item_code   text,
    customer_description text,
    product_id           integer NOT NULL REFERENCES public.products(id),
    case_size_lb         numeric(14,4) CHECK (case_size_lb > 0),
    created_at           timestamptz NOT NULL DEFAULT clock_timestamp(),
    created_by           text,
    updated_at           timestamptz NOT NULL DEFAULT clock_timestamp(),
    alias_key            text GENERATED ALWAYS AS
        (lower(regexp_replace(btrim(coalesce(customer_item_code, customer_description)),
                              '\s+', ' ', 'g'))) STORED,
    CHECK (customer_item_code IS NOT NULL OR customer_description IS NOT NULL)
);
CREATE UNIQUE INDEX IF NOT EXISTS customer_product_aliases_uidx
    ON public.customer_product_aliases (customer_id, alias_key);
CREATE INDEX IF NOT EXISTS idx_customer_product_aliases_desc
    ON public.customer_product_aliases
       (customer_id, lower(regexp_replace(btrim(customer_description), '\s+', ' ', 'g')))
    WHERE customer_description IS NOT NULL;

-- Customer PO number + document link on sales orders.
ALTER TABLE public.sales_orders
    ADD COLUMN IF NOT EXISTS customer_po text,
    ADD COLUMN IF NOT EXISTS source_document_id integer
        REFERENCES public.purchase_documents(id);
-- Dedupe lookup (warn-only, no unique constraint — mirrors ER dedupe).
CREATE INDEX IF NOT EXISTS idx_sales_orders_customer_po
    ON public.sales_orders (customer_id,
        lower(regexp_replace(btrim(customer_po), '\s+', ' ', 'g')))
    WHERE customer_po IS NOT NULL;
CREATE INDEX IF NOT EXISTS idx_sales_orders_source_doc
    ON public.sales_orders (source_document_id)
    WHERE source_document_id IS NOT NULL;

COMMIT;
```

## `extraction.py`

`extract_purchase_document(file_bytes, mime_type, kind='purchase')`.
`kind='sales'` selects `SALES_EXTRACTION_TOOL` + `SALES_EXTRACTION_PROMPT`,
validated by `SalesExtractionResult`:

* `customer_name: str` — the BUYER who issued the PO, never Seven Wells
  Granola (prompt states this explicitly: on a customer PO we are the vendor).
* `po_number: str|null`, `document_date: str|null`,
  `requested_ship_date: str|null` (same strict YYYY-MM-DD validator).
* `lines: [{customer_item_code: str|null, description: str (verbatim),
  quantity: number (>0, finite), unit: str|null, unit_price: number|null}]`.

Same rules as ER: no guessing (null), verbatim descriptions,
ordered-not-shipped, exclude freight/tax/deposit/total rows. No DB imports;
`EXTRACTION_MODEL` env unchanged; `anthropic==0.69.0` pin unchanged.

## Endpoints (all on DASHBOARD_KEY_ALLOWLIST; master key also works)

Shared refactor: the body of `/expected-receipts/extract` becomes
`_upload_intake_document(request, response, file, kind)` — validation,
magic-byte sniffing, PDF page cap, sha256, advisory-lock dedupe/resume,
row-first-then-Storage, `upload_failed` healing, `extraction` rate bucket —
all unchanged and shared. The sha256 resume query gains
`AND document_kind = %s` (the same bytes can legitimately exist once per
kind). `/expected-receipts/extract` delegates with `kind='purchase'`.

### 1. `POST /sales/orders/extract` — multipart `file`

`_upload_intake_document(..., kind='sales')`.
`201 {document_id, storage_path, already_seen, status}` (200 on resume).
Errors identical to ER: 413/415/422/429.

### 1b. `POST /purchase-documents/{id}/extract` — existing route, kind-aware

Reads the row's `document_kind`, passes it to `extract_purchase_document()`.
Same status guards and outside-transaction model call; same response shape
with the sales extraction payload.

### 2. `POST /sales/orders/match` — JSON `{extraction}`, pure read

Re-called by the dashboard whenever the user changes the customer.

```
{ customer: { match|null, confidence: exact|none, candidates (≤5, names+aliases LIKE) },
  duplicate_warning: { existing: [{order_id, order_number, status, total_lb,
                                   requested_ship_date, created_at}] } | null,
  lines: [{ customer_item_code, description, quantity, unit, unit_price,
            match_source: alias|exact|fuzzy|none, confidence,
            product|null, candidates (≤5),
            case_size_lb|null, case_size_source: alias|product|unit_is_lb|none,
            quantity_lb|null }] }
```

Customer: exact name → `customer_aliases` exact → candidates. Never
auto-creates. **[A]** No create-customer in V1: pick existing or abort.

Line match chain — alias → exact → restricted fuzzy → human:

* **Alias**: `customer_product_aliases` by normalized item code, then by
  normalized description (latest `updated_at` wins).
* **Exact**: odoo_code / exact-name tier — but an exact hit on a
  `label_type='private_label'` product is discarded (demoted to no-match)
  unless the product has prior sales for this customer. An exact text
  collision must not leak another customer's SKU.
* **Restricted fuzzy**: keyword/trigram tiers run only against the
  customer's prior-sales pool; candidate lists obey the same pool. Another
  customer's private-label products can never appear in any suggestion.
* **[A]** Prior-sales pool excludes cancelled orders AND cancelled lines:
  `SELECT DISTINCT sol.product_id FROM sales_order_lines sol
   JOIN sales_orders so ON so.id = sol.sales_order_id
   WHERE so.customer_id = %s AND so.status <> 'cancelled'
     AND sol.line_status <> 'cancelled'`.
* No customer resolved → all lines `match_source: 'none'`, empty candidates;
  the dashboard re-matches after a customer is picked (ER supplier pattern).

Quantity → lb (no description parsing, no kg — customer POs order finished
goods): unit says lb → `quantity_lb = quantity` (`unit_is_lb`); otherwise the
unit defaults to cases and `case_size_lb` comes from alias → else
`products.case_size_lb`, applied only when match_source is alias/exact (or
after an explicit human pick, computed client-side like ER's `chosen` flow).
Fuzzy/none lines keep `quantity_lb` null until confirmed.

**[A]** Unit price: extracted and shown on the review screen; stored to
`sales_order_lines.unit_price` only when the basis is unambiguous — per-case
price on a cases line, or per-lb price on a lb line; otherwise null with a
"price basis unclear" tag in the UI.

**[A]** Private-label warning (never a block): a `private_label` product
outside the customer's prior-sales pool that reaches a line via explicit
human pick gets an amber badge ("Private label — first sale of this SKU to
this customer") and a response warning. Approve is never blocked by it.

### 3. `POST /sales/orders/extract/approve`

```
{ document_id, customer_id, customer_po,           ← required, non-empty
  order_date?, requested_ship_date?, notes?,
  lines: [{ product_id, quantity, unit: 'cases'|'lb', case_size_lb|null,
            quantity_lb, unit_price|null,
            customer_item_code|null, customer_description, save_alias }],
  force: false }
```

One transaction, mirroring ER approve: document `FOR UPDATE` +
`document_kind='sales'` + `status='extracted'` guards → customer exists +
active → `pg_advisory_xact_lock` on `so-intake-po:{customer_id}:{norm po}` →
dedupe → `409 DUPLICATE_PO` with `existing` unless `force` → finite-positive
validation on quantity/case_size_lb/quantity_lb → `ALIAS_CONVERSION_MISMATCH`
(422) when `save_alias` + `case_size_lb` doesn't explain `quantity_lb` ±0.01
on a cases line → **`_create_sales_order_core()`** (factored from
`create_sales_order`; manual + approve paths share header/line inserts,
service-item handling, low-quantity warnings) inserting the SO with
`status='confirmed'` **[A]**, `customer_po`, `source_document_id`, per-line
notes auto-composed (`"PO <po>: <customer description> — <qty> <unit>"`) →
alias upserts (ON CONFLICT (customer_id, alias_key), latest wins) → document
`status='approved'`, `approved_at`. Private-label out-of-pool lines add
warnings (never block).

`201 { order_id, order_number, customer, total_lb, lines, aliases_saved,
duplicate_overridden, warnings }`

### 4. `GET /purchase-documents/{id}/url` — unchanged, shared.

Rate limits: shared `extraction` / `signed_url` buckets cover both kinds.

## Review screen (New Sales Order modal)

New `so-modal` opened by a "New Sales Order" button on the Sales Orders tab,
structured like `er-modal`: dropzone (PNG/JPG/PDF + ⌘V clipboard paste via
the existing clipboard helpers) → upload → extract (90 s browser timeout) →
review. **[A] V1 is intake-only** — no manual create form in the modal;
`POST /sales/orders` stays off the dashboard allowlist (GPT keeps manual
creation; the endpoint auto-creates customers, unsafe under the
browser-shipped key).

**[A]** The review state machine is shared: `er-intake-logic.js` is RENAMED
to `intake-logic.js` as a new file (old file deleted, no shim, single
cache-bust bump), parameterized with a small sales config (cases-default
units, `unit_price`, no lb-parsing sources). node:test suite covers both
configs.

Fields:

* **Header** (2-col grid): filename + view link (signed URL) · Customer
  (badge Exact/None + candidate dropdown) · **Customer PO #** (required —
  empty blocks Approve) · Order date · Requested ship date.
* **Duplicate banner** when (customer, normalized PO) exists — order numbers,
  statuses, links; "Create anyway" arms `force` (invalidated on customer/PO
  edit via `forceKey`).
* **Line cards** (row-118 stacked-card layout): item code + verbatim
  description (read-only) / product row: match badge (Alias / Exact /
  Fuzzy n% / Chosen / No match) + picker (**[A]** full catalog, customer's
  prior-sales products listed first, amber private-label warning outside the
  pool) + Change / qty × unit (cases default) → case_size_lb (source-tagged:
  alias / product / —) → computed lb (amber "needs lb" when empty) / unit
  price (editable; "price basis unclear" tag when ambiguous) / footer:
  Include + Save alias checkboxes.
* **Sticky footer**: "Approve — create order · N of M line(s) · X lb total",
  blockers named ("N line(s) need a product or case size", "PO number
  required"). Approve disabled while matching (input locking) and after a
  failed re-match (Retry-matching button) — same guards as ER.
* Paperclip on SO rows with `source_document_id` → signed URL (ER pattern).
